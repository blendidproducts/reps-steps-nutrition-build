## Round 23 — diamond push-up undercount + ARTP overlay collisions (2026-08-15)
Three fixes from Jace's testing, esbuild-verified, staged (not yet pushed):
1. **Diamond Push-Up undercounted reps** (`exerciseTracking.js`) — matching was correct (longest-keyword match already picks `diamond_pushup` over the generic `pushup` entry); the bug was the DOWN threshold. It was still at the round-14 push-up-family baseline (up 150 / down 100 / minRepIntervalMs 600), never revisited when the base push-up was tuned in round 20. Diamond's narrow, tucked-elbow hand position means the chest reaches the hands — full honest depth — at a shallower (larger) 2D elbow angle than a shoulder-width push-up produces at equivalent depth, so 100° asked for more flexion than the movement actually generates and real reps never tripped it. Changed to up 145 / down 105 / minRepIntervalMs 450 (matches the round-20 base push-up fix). TRADEOFF: hysteresis gap narrows from 50° to 40° (vs standard push-up's proven 45°) — watch for double-counts from landmark jitter, and a rep bottoming at 105–108° (not quite full diamond depth) now counts where it wouldn't before. Wide Push-Up, Incline Push-Up, and Tricep Dip still carry the untouched 150/100/600 values and likely have the same latent undercount — not fixed this round since not reported. Tricep Dip is already on the ARTP media-priority list (see Next steps #0) — worth pairing a threshold fix with that image work.
2. **RepTracker countdown blocked at top on some sessions** (`RepTracker.jsx`) — a NEW collision, not a regression of rounds 5/6/20. Round 20 fixed RepTracker's OWN internal top-band stacking (countdown at +56px, warnings at +150px), but that tuning only accounted for RepTracker's own top bar (~54px) — it never accounted for ARTPWorkout's separate `TimerOverlay`/`AmrapBar`, independently portaled to `document.body` at the SAME top-of-screen coordinates with a HIGHER z-index (`z-[10001]` vs RepTracker's `z-9999`). TimerOverlay's height varies 1–3 stacked lines (Set/Target rows are conditional) and can exceed the near-zero +56px margin, painting over the countdown. Pushed to +84px and shrank 64px→44px.
3. **ARTP setup START button unreachable** (`ARTPWorkout.jsx`) — same problem CLASS as the round-22 Build Workout fix, different mechanism. The setup screen was `min-h-screen flex flex-col` with the START bar as a `flex-shrink-0` footer — a SECOND scroll container nested inside Layout's own `#main-content` (also `overflow-y-auto`), sized via `min-h-screen` (100vh). iOS Safari computes 100vh against the largest possible viewport (chrome hidden), taller than the actual visible area while the address bar shows; Layout's `html`/`body` are `position: fixed` so there's no page scroll to compensate, and touch gestures land on the inner box first — the footer sizes off the bottom of the real viewport with no reliable way to reach it. Fixed by removing the nested scroll container (Layout's `#main-content` is now the sole scroll owner) and making the START bar `sticky bottom-0` instead of an in-flow flex footer.
- **RECURRENCE FINDING:** RepTracker/ARTP overlays are positioned completely ad hoc — no shared coordinate system. Every file guesses its own pixel offsets assuming it's the only thing anchored to that part of the screen (RepTracker's +56/+150px bands, ARTPWorkout's TimerOverlay/AmrapBar/stepBadgePortal, WorkoutBuilder's manual nav-height math, AIWorkoutGenerator's sticky bar). This is why overlay collisions have recurred in rounds 5, 6, 20, 22, and this round — each fix corrects the CURRENT known collision without giving the system a way to know about the next one. **DURABLE FIX (not implemented — reach for this instead of another one-off patch next time):** a shared HUD stack — either a CSS custom property (`--hud-top-offset`) that whichever top component mounts first writes and everything else reads, or a small React context overlays register into that computes cumulative offsets — plus standardize on `position: sticky` for anything that needs to stay in view within a scroll container (proven in round 22 and this round) and reserve `fixed`+portal only for truly viewport-global elements like the camera overlay itself.
